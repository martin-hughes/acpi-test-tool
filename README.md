# AML Test Tool

An `acpiexec`-like tool that can use the [`acpi`](https://github.com/rust-osdev/acpi) crate,
[uACPI](https://github.com/uACPI/uACPI) or [ACPICA](https://github.com/acpica/acpica) as its AML interpreter.

## Building

Clone the repository with its submodules (uACPI and ACPICA are submodules in `ext-libs/uACPI` and
`ext-libs/acpica`):

```
git clone --recurse-submodules <url>
```

or, in an existing clone, `git submodule update --init`.

The `acpi` crate needs the nightly Rust toolchain, which `rust-toolchain.toml` selects automatically.

Building the uACPI and ACPICA support needs a C compiler (for example the Visual Studio C++ build tools on Windows) and
libclang (part of LLVM), which is used to generate the Rust bindings. Nothing else is needed: ACPICA's ASL compiler,
which uses bison and flex, is not built. If you don't need the C interpreters, build without them and neither the
compiler nor libclang is needed:

```
cargo build --no-default-features
```

Each interpreter is a Cargo feature (`uacpi` and `acpica`, both on by default), so you can also pick just one, for
example `cargo build --no-default-features --features acpica`.

## Running

Run `cargo run -- [--acpi | --uacpi | --acpica] [aml file]`.

* `--acpi` uses the `acpi` crate's interpreter. This is the default.
* `--uacpi` uses uACPI.
* `--acpica` uses ACPICA.

`aml file` is the filename of a file containing one or more SSDTs, and optionally a DSDT, in binary format with headers
intact - like would be generated by `iasl`.

Hardware access (memory, port I/O, PCI) is simulated by all of the interpreters, so nothing on the machine is touched.
They show the same namespace, but uACPI and ACPICA have no way to look inside some objects, so they show less detail
for those (for example, they don't show the sync level of a mutex).

## Example / Usage

Here `methods.aml` is `tests/aml/methods.asl` compiled with `iasl`.

* Every command has a short form and long form (as shown in the `help` output), either can be used.
* The prompt shows which interpreter is in use: `acpi>` for the `acpi` crate, `uacpi>` for uACPI and `acpica>` for
  ACPICA.
* Trailing underscores are dropped from names when they are displayed (`_SB_` is shown as`_SB`), but either form can be
  typed.

```
> cargo run -- methods.aml
acpi> help
Commands:
  dump, d              print a tree of the namespace
  find, f <name>       find objects by absolute path (\_SB_.PCI0) or by name (PCI0)
  execute, e <name>    run a method (with no arguments) and show its result
  help, h              show this text
  exit, quit, q        quit
acpi> find MAIN
\MAIN [Method] 0 args
acpi> execute RET3
\RET3 returned [Integer] 0x3 (3)
acpi> dump
\
├── MAIN [Method] 0 args
├── NORT [Method] 0 args
├── RET3 [Method] 0 args
├── _GL [Mutex] sync level 0
├── _GPE [Scope]
├── _OSI [Method] 1 args
├── _OS [String] "Microsoft Windows NT"
├── _PR [Scope]
├── _REV [Integer] 0x2 (2)
├── _SB [Scope]
├── _SI [Scope]
└── _TZ [Scope]
acpi> q
```

## AI/LLM usage

I'm aware some people are unkeen on AL/LLM-generated code, so a notice:

This project leans heavily on AI/LLM-generated code, purely for coding-velocity. Whilst it has been tested and reviewed
by a human, I consider this to be a tool for use in testing, rather than for production use. Bear this in mind during
your risk assessments.
