# Plan

## Outline

To create a tool similar to `acpiexec` that loads an AML file using an AML interpreter, then presents a TUI for the
user, allowing them to interrogate the ACPI Namespace or to execute methods.

## MVP:

A tool that:

* Takes one command line argument (the name of an AML binary file)
* Loads it using the `acpi` crate
* Prints out any errors
* Allows the user to enter commands:
  * `dump` will dump a tree view of the namespace
  * `find [name]` will search the namespace for `[name]`, and dump the object found, and its type.
  * `execute [name]` runs a method that takes no arguments and displays its result (added after the initial MVP).
  * `exit` to quit.

### The TUI

* The TUI will be REPL-style, with output printed and then the opportunity for a user to enter commands.
* `rustyline` or a similar crate should be used.

### Design decisions

* Input files are ACPI tables that include the 36-byte SDT header. A single file may contain several tables back to
  back. Only `DSDT`/`SSDT` tables are loaded; others are skipped with a message.
* The namespace is left as the loader produced it: no `_INI`, `_STA` etc. are run.
* `find` accepts either an absolute path (`\_SB_.PCI0`), which must match exactly, or a bare name / partial path
  (`PCI0`, `DEV0.FOO_`), which matches anywhere in the namespace. All matches are printed. Names shorter than four
  characters are padded with `_`.
* Output is a type and value summary (integers, strings, buffers, method arg counts, region and field details).
* `dump` prints an ASCII tree with the type of each node.
* Interpreters sit behind the small `AmlBackend` trait, which only loads tables and lists namespace entries. Searching
  and rendering are backend-neutral. `execute`/`set` would be added to the trait later.
* Host hardware access (memory, I/O, PCI) is stubbed with `NullHandler`, which returns zero.

### Tech stack

Use Rust and Cargo throughout. The `acpi` crate needs the nightly toolchain (`rust-toolchain.toml` selects it).

### Dependencies

The only restrictions on dependencies are:

* They must all be available on `crates.io` with no significant CVEs.
  * There are two exceptions, both from the `main` branch of `https://github.com/rust-osdev/acpi`:
    * the `acpi` crate itself, instead of the crates.io version.
    * `aml-test-tools`, which provides `NullHandler` and `new_interpreter`. It is not published to crates.io.
  * uACPI and ACPICA are C, not crates. Each is a git submodule (`ext-libs/uACPI` and `ext-libs/acpica`), compiled by a
    `-sys` crate (`uacpi-sys`, `acpica-sys`) with the `cc` crate, with Rust bindings generated by `bindgen` at build
    time. Support for each is behind a Cargo feature (`uacpi` and `acpica`, both on by default) so that the tool can
    still be built without a C toolchain or libclang.

### The C interpreters (uACPI and ACPICA)

* The input's AML tables are wrapped in a made-up RSDP, XSDT, FADT and FACS, because that is what they start from.
  A file with no DSDT gets an empty one, and only one DSDT is allowed (extra ones are reported and ignored). Table
  checksums are corrected, since the `acpi` crate doesn't check them. This is shared code (`src/firmware.rs`).
* As with the `acpi` crate, the namespace is loaded but not initialised, so no `_INI` or `_STA` methods run.
* Memory, port I/O and PCI access are simulated (unmapped memory and PCI read as zero, and port I/O is a block of memory
  that reads back what was written) so nothing on the host is touched. This is shared code too (`src/hostsim.rs`).
* Each interpreter reports load errors differently: uACPI logs them and carries on, and ACPICA prints them but can
  still return success. The backends count the errors they see, so that the usual "the namespace may be incomplete"
  message appears for all three.
* They keep global state, so a process can only use one instance of each.

### uACPI

* uACPI has no public way to inspect operation regions, fields or mutexes, so those show no detail.

### ACPICA

* Only the core interpreter is built (no debugger, disassembler or ASL compiler).
* ACPICA prints its diagnostics through a printf-style function, which Rust can't define, so `acpica-sys/shim.c`
  formats them and passes them to Rust. Informational lines (`ACPI: ...`) are hidden; warnings and errors go to stderr.
* The predefined `\_SB_` and `\_TZ_` are a Device and a ThermalZone in ACPICA, but are shown as scopes, as in the other
  interpreters.
* Like uACPI, ACPICA has no way to look inside operation regions, fields or mutexes.
